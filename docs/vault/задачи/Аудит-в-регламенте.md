# Аудит в регламенте — периодическая процедура

Статус: задел (реализация после «Навыка аудита»)
Дата: 2026-08-20

## Проблема

Навык `reglament-audit` запускается вручную. Разовый аудит
полезен, но проект стареет непрерывно: код растёт, зависимости
устаревают, долг копится. Без процедуры повторения аудит
останется однократным действием, о котором забудут.

Записать в регламент «раз в месяц делать аудит» недостаточно:
такой пункт ничем не подкреплён, месяцы никто не считает.
Ровно та ситуация, из-за которой появился принцип 10.

## Механика — что хук РЕАЛЬНО может

Проверено по устройству `check_turn_end.py`.

Хук НЕ запускает навык. Единственный канал воздействия —
`{"decision": "block", "reason": "..."}`, где текст `reason`
уходит АССИСТЕНТУ как инструкция. Дальше ассистент читает её и
действует сам.

Отсюда цепочка:

1. Счётчик закрытых задач растёт в `close_task.py`.
2. Хук сравнивает счётчик и дату последнего аудита с порогом.
3. Порог превышен — хук блокирует завершение хода ОДИН РАЗ и
   отдаёт ассистенту инструкцию предложить аудит.
4. Ассистент предлагает, пользователь решает.
5. Отказ записывается в табло, чтобы не спрашивать на каждой
   следующей задаче.

## Слабое место — назвать честно

Между «ассистенту сказали предложить» и «пользователь
запустил» есть зазор. Ассистент может предложить вяло,
пользователь отмахнуться.

Это слабее, чем `gate_edit.py`, который просто не даёт править
файл. Сильнее сделать нельзя: аудит — процедура на полчаса с
диалогом, её невозможно запустить принудительно посреди чужой
задачи.

Механизм честно называется «не даёт забыть», а не
«заставляет». Записать это в описание, чтобы не создавать
ложных ожиданий.

## Почему отдельная задача

Счётчик задач класть некуда. Табло `task-state.json` описывает
ТЕКУЩУЮ задачу; накопительный счётчик меняет его назначение.
Это правка `close_task.py`, возможно `approve_task.py` и
формата табло — то есть вмешательство в работающие скрипты со
своими рисками регрессии.

Граница разбиения: новое отдельно, правка работающего
отдельно.

## Нерешённое

**Порог.** Сколько закрытых задач до предложения аудита —
неизвестно. Данных нет: один прогон на одном проекте. Взять
любое разумное число и поправить по опыту; в описании честно
пометить как подобранное, а не выведенное.

**Считать задачи или дни.** Задачи надёжнее (их закрытие уже
проходит через скрипт), но проект может простоять полгода без
задач и всё равно устареть — зависимости стареют сами.
Возможно, нужны оба условия.
