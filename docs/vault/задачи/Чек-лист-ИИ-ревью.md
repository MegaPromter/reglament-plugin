# Чек-лист ИИ-ревью — воспроизводимая проверка смысла

Статус: проект
Дата: 2026-08-20

## Проблема

ИИ-ревью ловит то, что не ловит ни один линтер: неверную
бизнес-логику, расползание архитектуры, пропущенные проверки
прав. Но в открытой форме («проверь код») оно невоспроизводимо —
каждый прогон охватывает случайный набор тем, и невозможно
узнать, что осталось непроверенным.

Фиксированный список делает воспроизводимой не находку, а
ОБЛАСТЬ проверки. Находки могут отличаться, охват — нет.

## Граница с линтерами

Пункт, который ловится линтером, в чек-листе быть НЕ должен:
это трата токенов на работу, которую скрипт делает бесплатно
за миллисекунды.

Правило разделения: линтеру — то, что определяется по ФОРМЕ
кода; ИИ — то, что требует понимания СМЫСЛА.

Пример разницы. «Есть ли `except: pass`» — форма, это ruff.
«Есть ли места, где ошибка проглатывается и пользователь видит
успех вместо провала» — смысл, линтер не найдёт никогда.

## Две части чек-листа

**Универсальная** — верна для любого Django-проекта, пишется
заранее, живёт в плагине.

**Проектная** — вытекает из решений конкретного проекта
(«логика в сервисах, не во views», «деньги в копейках целым
числом»). Заранее не пишется: правила из чужого проекта хуже,
чем их отсутствие — ассистент будет подгонять код под
несуществующую структуру.

Решение по хранению: ДВА файла.
- универсальная часть — шаблон в `templates/`, обновляется
  вместе с плагином, улучшение доходит до всех проектов;
- проектная — бланк, копируемый в vault проекта и заполняемый
  при заходе.

Минус (принят): при ревью читаются два файла вместо одного.

## Универсальная часть — предмет проверки

Список тем, по каждой обязателен вердикт. Формулировки
уточняются при написании шаблона.

1. **Права доступа.** Есть ли обработчики, доступные без
   проверки авторизации там, где она подразумевается. Линтер
   не знает, какая страница должна быть закрытой.
2. **Запросы в цикле.** Обращение к связанным объектам внутри
   обхода — источник N+1. Статикой не ловится, но по коду
   часто виден намёк.
3. **Проглоченные ошибки.** Не форма `except`, а следствие:
   сбой скрыт, вызывающий код считает операцию успешной.
4. **Смысловые дубли.** Несколько функций делают одно и то же
   разными словами. Текстовые детекторы копипасты слепы —
   код не совпадает буквально.
5. **Код против реальности.** Ссылки на несуществующее: имена
   маршрутов в шаблонах, поля моделей, ключи настроек.
6. **Данные без проверки.** Пользовательский ввод, попадающий
   в запрос, файловый путь или вывод без валидации.
7. **Секреты и жёстко вписанные значения.** Пароли, ключи,
   адреса, зависящие от окружения.
8. **Необработанные границы.** Внешние вызовы без таймаута,
   отсутствие ветки на пустой результат.
9. **Расхождение с документацией.** Код делает не то, что
   написано в заметках vault и CLAUDE.md.

## Проектная часть — вопросник

По принципу 10: «спросить пользователя про правила проекта» —
регулярное действие, значит это список, а не импровизация.

Порядок работы вопросника:

1. Ассистент задаёт вопросы из списка.
2. На ответ «не знаю» (частый случай: проект писался
   нейросетью, решения принимались без ведома пользователя)
   ассистент НЕ пропускает пункт, а идёт читать код и
   возвращается с найденным на согласование.
3. Обнаруженное расхождение — само по себе находка. Формат
   возврата: «вижу два подхода — такой в N местах, такой в M;
   какой считаем правильным».
4. Согласованный ответ становится пунктом проектного
   чек-листа.

Вопросы задаются одним списком, не порциями. Чек-лист
работоспособен и при частичном заполнении: незаполненные
пункты просто не проверяются, бланк не блокирует ревью.

Вопросы (черновой состав):

- Где лежит бизнес-логика: во views, в моделях, в отдельном
  слое сервисов?
- Могут ли приложения обращаться к моделям друг друга напрямую?
- Есть ли зоны, которые нельзя трогать без отдельного
  разрешения?
- Как хранятся деньги, даты, единицы измерения?
- Откуда берутся настройки окружения?
- Какие внешние сервисы вызываются и что делать при их отказе?
- Кто имеет доступ к каким разделам?
- Что считается обязательным при добавлении новой страницы
  (проверка прав, тест, запись в документацию)?
- Какие соглашения по именованию действуют?
- Что уже известно как «сделано плохо, но переделывать пока
  не будем»?

Последний вопрос важен отдельно: без него ревью будет каждый
раз заново находить осознанно принятый долг и тратить на него
внимание.

## Формат ответа ревью

Действуют три требования из заметки «Стратегия контроля
качества кода»:

1. Каждая находка содержит путь к файлу, номер строки и
   дословную цитату кода. Без цитаты находка вычёркивается.
2. Вердикт по КАЖДОМУ пункту, включая «нарушений нет».
3. Факт отдельно от суждения.

Дополнительно: ревью не правит код. Результат — список находок
на решение пользователя. Правки идут отдельной задачей.

## Что меняется в файлах

- новый `templates/checklist-review.md` — универсальная часть;
- новый `templates/checklist-project-blank.md` — бланк
  проектной части и вопросник;
- `SKILL.md` — шаг копирования бланка в vault проекта.

Оба шаблона пишутся с пометками `[МАСТЕР: …]` по конвенции
репозитория и переводятся мастером на язык проекта.

## Как проверим

Прогон на реальном проекте (planapp_django): пройти вопросник,
получить заполненный проектный чек-лист, выполнить по нему
ревью. Признак работоспособности — находки, которые не даёт
ни один линтер, и отсутствие пунктов, дублирующих ruff.

## Уточнить

Объём универсальной части. Девять тем — предположение;
на реальном прогоне часть может оказаться пустой (никогда
ничего не находит) или наоборот слишком широкой для одного
прохода. Корректируется по факту, не заранее.
