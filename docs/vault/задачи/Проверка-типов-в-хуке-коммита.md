# Проверка типов (mypy) — вопрос мастера и шаг в хуке коммита

Статус: сделано
Дата: 2026-08-31
Форма: малая

## Проблема

В planapp_django (коммит 9557a1f) в местный хук
`.claude/hooks/pre-commit-tests.sh` добавлен прогон mypy ПЕРЕД
pytest: типы проверяются за секунды (замер 2026-08-31: тёплый кэш
0,9–2,3 с, холодный 7,3 с), тесты идут ~2 минуты. Красные типы
отсеиваются дёшево, без тестового прогона.

Правка живёт в одном проекте. Шаблон плагина её не знает, и каждый
новый проект получает хук без этого шага.

## Чем местная копия не годится как есть

1. **Блокировка всех коммитов там, где mypy нет.** Местный вариант
   включается по наличию `venv/Scripts/python.exe`. В проекте, где
   venv есть, а mypy не ставили, `python -m mypy` вернёт «No module
   named mypy» — и хук заблокирует ЛЮБОЙ коммит. Шаблон едет в
   чужие проекты, для него это отказ системы.
2. **Путь интерпретатора только под Windows.** `venv/Scripts/
   python.exe` на macOS/Linux не существует.

## Решение: типизация — решение проекта, а не автоопределение

Первый черновик включал шаг молча, по факту установленного mypy.
Отвергнуто: бывает проект, где mypy настроен, а типы прямо сейчас
красные (конфиг есть, ошибки копятся, в CI гоняют «для сведения»).
Установка регламента заблокировала бы там ВСЕ коммиты, а человек
соглашался на «тесты перед коммитом» и не понял бы, откуда это.

Ведём ли мы типизацию — такая же конвенция проекта, как команда
тестов. Значит её спрашивает мастер.

### Что меняется в мастере

**Шаг 2, анкета** — новый вопрос после «Команды тестов», задаётся
ТОЛЬКО если в ответе про стек есть Python (mypy к Go или PHP
отношения не имеет; вопрос без смысла учит жать «да» не глядя).
Формулировка по правилу 5 («что это → зачем → куда пойдёт»),
человеческим языком: типы — это пометки, какого рода данные ждёт
каждая функция; отдельная программа находит несостыковки заранее,
за секунды; ответ пойдёт в устав и в хук коммита; проверка
включится сама, когда mypy будет установлен, до тех пор не мешает.

**Шаг 3, устав** — при ответе «да» в секцию «Конвенции кода»
строка: новый код пишем с аннотациями типов, перед коммитом типы
проверяются наравне с тестами. При «нет» секция не меняется.

**Шаг 8, хук** — при «да» в `pre-commit-tests.sh` пишется блок
проверки типов перед тестами; при «нет» блок не пишется вовсе. В
шаблоне блок помечен `[МАСТЕР: если типизация «нет» — удалить
весь блок ниже]`. Строку в таблице хуков дополнить: «тесты перед
коммитом; при выбранной типизации — сначала проверка типов».

**Режим обновления** — устав он не трогает никогда, поэтому там
свой вопрос, в таблице состояния: «в шаблоне появился шаг проверки
типов, у вас его нет — включить?». Молча дописывать в чужой хук
шаг, блокирующий коммиты, нельзя.

### Как устроен сам блок в хуке

**Поиск интерпретатора — по соглашению плагина.** Как в
`collect_audit.py` (функция `питон`): перебор `.venv`, `venv`,
`env` × `Scripts/python.exe`, `bin/python`; не нашлось — голое
`python`, как в остальном этом хуке.

**Два предохранителя по кодам возврата mypy** (проверено на mypy
2.3.1):

- `python -m mypy --version` молча, в никуда. Провал — mypy не
  установлен, шаг пропускается. Это не подстраховка, а условие
  работоспособности: на новом проекте в момент настройки mypy ещё
  нет, и без этого предохранителя ответ «да» заблокировал бы
  первый же коммит.
- сам прогон: код 1 — найдены ошибки типов, коммит блокируется;
  код 2 — mypy не смог запуститься (не задана цель проверки,
  битый конфиг), это не про код проекта, коммит не трогаем;
  код 0 — чисто.

Разделение по кодам заменяет разбор конфигов (`mypy.ini`,
`[tool.mypy]` в `pyproject.toml`): цель проверки задаётся четырьмя
разными способами, перечислять их в хуке — лишняя хрупкость.
Сознательная плата: сломанный конфиг mypy тихо выключает проверку,
а не кричит. Для хука, который едет в чужие проекты, отказ в
сторону «пропустить» правильнее отказа в сторону «всё
заблокировать».

**Имена переменных в этом шаблоне — латиницей** (`PY`,
`MYPY_STATUS`), в отличие от Python-шаблонов: bash кириллические
имена не принимает (проверено — «command not found»). Комментарии
русские, как в остальном файле.

## Границы

Только Python и только mypy. Логика предохранителей завязана на
коды возврата именно mypy; у `tsc` в TypeScript они другие, одним
шаблоном не покрыть. Аналог для TypeScript — отдельная задача,
когда появится проект, которому это нужно.

`Регламент.md` (десять принципов) не меняется: типизация — не
принцип ведения разработки, а конвенция кода, её место в уставе.

Версия 1.4.5 в `plugin.json` и `templates/VERSION`.

Реализовано в коммите a11b81d (2026-08-31), отправлено на
GitHub 2026-09-01 (`5384195..2c66350`).

## Как проверим

Прогон шаблона подачей JSON на stdin, mypy берём из venv
planapp_django (mypy 2.3.1):

1. команда не коммит → выход 0, mypy не запускался;
2. проект без mypy (голый временный репозиторий) → коммит
   проходит, в выводе про типы ни слова;
3. mypy есть, цель не задана (код 2) → коммит проходит;
4. mypy есть, файл с красными типами (код 1) → блок, код 2,
   сообщение «Проверка типов не прошла»;
5. mypy есть, типы чистые (код 0) → доходит до тестов;
6. типы чистые, тесты красные → блок на тестах (прежнее
   поведение не сломано);
7. интерпретатор находится и в `venv/Scripts/python.exe`,
   и в `.venv/bin/python`.

8. вариант «нет»: блок вырезан по пометке `[МАСТЕР: …]` —
   файл разбирается bash и ведёт себя ровно как до правки.

**Факт: 13 из 13 зелёные.** Вариант «нет» — 34 вырезанные
строки, хвост файла совпадает с версией 1.4.4, красные тесты
по-прежнему блокируют коммит. `py_compile` шаблонов чист
(Python-файлы не трогали, прогнан как тест проекта).

Тексты мастера (вопрос анкеты, строка устава, пометка `[МАСТЕР:
…]`, строка таблицы хуков, вопрос режима обновления) — сверка
глазами: формулировки на месте, вариант «нет» нигде не оставляет
следов в файлах проекта.
