# Навык reglament

**Язык общения на всех шагах:** сначала человеческое название,
в скобках — имя из кода («комментарий к работе (`WorkComment`)»,
а не «`WorkComment`»). Без перевода допустимы только файлы и
папки. Нельзя согласовать то, что непонятно.

Механизирует регламент проекта (`docs/vault/_meta/Регламент.md`).
Навык не пишет код сам — он ведёт сессию по обязательным шагам.
Часть шагов принуждается хуками (скриптами-перехватчиками) — их
нельзя пропустить даже случайно. Если какой-то шаг неприменим —
остановиться и спросить пользователя (правило 8 регламента).

Слэш-команды (`/reglament` и другие) пользователь вводит в ПОЛЕ
ЧАТА. Никогда не оформлять их shell-блоком: у блока появится
кнопка Run, терминал такой команды не знает и вернёт ошибку.
Shell-блок — только для настоящих команд терминала.

Действий в терминале пользователю не поручать. Единственное его
действие в процедуре — **клик по карточке вопроса** на шаге
согласования (и выбор варианта интерфейса на шаге 3.5).

## Табло задачи — обновлять на каждом шаге

`.claude/task-state.json` (локальное, вне git) — машиночитаемое
состояние: задача, путь к заметке, фаза, форма, отметка
одобрения. Фазы: `vault` → `заметка` → `согласовано` → `код` →
`тесты` → `коммит` → `закрыто`. Навык обязан обновлять табло при
каждом переходе — хуки читают именно его:

- `gate_edit.py` не пускает правки кода, пока полная форма не
  согласована (малая — пока фаза не «согласовано»);
- `check_commit.py` блокирует коммит без ссылки на vault;
- `check_turn_end.py` не даёт замолчать, если заметка ждёт
  согласования, а ход закончился без карточки и без вопроса;
- `validate_vault.py` проверяет vault при коммитах и закрытии;
- `close_task.py` закрывает задачу (хэш, статус, коммит, табло).

**Отметку «одобрено» в табло ассистент не ставит.** Источник
истины — ответ пользователя в стенограмме сессии; отметку
проставляет сам `gate_edit.py`, найдя этот ответ (чтобы задача,
продолженная в новой сессии, не согласовывалась заново).

## Вводная памятка

**По умолчанию — короткая** (3 строки, первым сообщением):

> Работаем по регламенту. Задача: «…», форма: полная/малая,
> фаза: «…». Код не правится до согласования заметки.
> (полная памятка — по слову «памятка»)

**Полная** (карта файлов системы: устав, vault, память ИИ, табло,
порядок работы — как в Регламенте) выводится только если:
- память ИИ проекта пуста или отсутствует — значит, это первая
  сессия на этой машине (новый человек или перенос), ИЛИ
- пользователь попросил: «памятка».

## Продолжение прерванной задачи

Если при старте в табло уже есть незакрытая задача (или команда
«/reglament продолжить»):

1. Прочитать табло: задача, фаза, заметка, форма.
2. Сверить с реальностью: заметка существует и её статус
   соответствует фазе; `git status` — нет ли чужих правок;
   `current_task.md` — открытые вопросы.
3. Доложить коротко: «В работе „…", фаза „…", продолжаю с шага N».
4. Табло расходится с реальностью — НЕ угадывать, спросить
   пользователя (правило 8).

## Шаги процедуры

Выполнять строго по порядку. Не переходить к следующему шагу,
пока не закрыт текущий.

### Шаг 0. Статус и контекст

1. Прочитать табло и файл памяти `current_task.md`: нет ли
   параллельной работы и незакрытых задач (если есть — ветка
   «Продолжение» выше).
2. `git status` — грязная папка чужими правками → выяснить у
   пользователя.
3. Завести табло новой задачи: фаза `vault`.

### Шаг 1. Сначала vault, потом код

Найти и прочитать релевантные заметки в `docs/vault/`
(модули → `модули/`, прошлые задачи → `задачи/`, решения →
`архитектура/`). Только после этого смотреть код.

### Шаг 2. Проект заметки

Сначала оценить размер: правка в 1–2 файлах, без изменения
бизнес-правил, без новых зависимостей и без миграций БД — это
**малая форма**: сказать «это малая форма, делаю так-то»,
получить подтверждение (фаза → `согласовано`), а после коммита
закрыть через `close_task.py --desc ... --files ...`.
При сомнении — спросить пользователя.

Иначе показать в чате ПРОЕКТ заметки по шаблону
`_meta/Шаблон — задача.md` (Зачем / Что именно делаем /
Затрагивает / Бизнес-правила / **Как проверим** / Связи /
История). Для модуля — `Шаблон — модуль.md`, для архитектурного
решения — `Шаблон — решение.md` (контекст → варианты → решение
→ последствия).

Правила проекта заметки:
- «Как проверим» обязательна: 2–5 проверяемых утверждений на
  языке пользователя; рекомендуемый формат «дано → когда →
  тогда». Без секции заметка не согласовывается.
- **Не угадывать**: недосказанное в требовании — маркер
  отдельной строкой «⚠️ уточнить: …». С неснятыми маркерами
  заметка не согласовывается (валидатор проверяет).
- Статус строго из словаря; термины сверять с
  `docs/vault/Глоссарий.md`.

Фаза табло → `заметка`. НЕ сохранять заметку и НЕ править код
до согласования.

### Шаг 3. Согласование

**Полная форма:** показав ПРОЕКТ заметки, задать карточку
вопроса (инструмент `AskUserQuestion`). В тексте вопроса —
название задачи из табло слово в слово: «Согласовать заметку
„{задача}"?». Варианты: **«Согласовано»** первым и «Нужны
правки»; вариант отказа обязателен.

**Подпись варианта — ровно «Согласовано», без добавок:**
согласование ищется точным совпадением (`gate_edit.py`,
`найти_согласование`), и подпись «Согласовано (рекомендую)» не
засчитается — правки кода останутся заблокированными молча.

Проект показан, но обсуждение затянулось (больше двух ходов) —
**показать заметку заново**: карточку согласования после долгого
обсуждения задавать нельзя, проект должен быть на виду.

Клик пользователя и есть согласование — ответ приходит тем же
ходом: ни штампов, ни команд в терминале, ни ожидания, ни
пробуждения сессии. Согласовать за пользователя нельзя:
`gate_edit.py` ищет в стенограмме сессии именно ЕГО ответ и до
него правку кода не пропустит.

- пришло «Согласовано» — сохранить заметку в
  `docs/vault/задачи/` со статусом `в работе`, фаза → `код`;
- пришло «Нужны правки» — поправить проект заметки и спросить
  карточкой снова.

Молча закончить ход в фазе `заметка` не даёт хук
`check_turn_end.py`: он один раз вернёт ассистента, если
согласования нет, а ход кончился не вопросом и не карточкой.

**Малая форма:** словесного «да» достаточно — перевести фазу в
`согласовано` вручную.

### Шаг 3.5. Варианты интерфейса (если он меняется)

Правило 14 устава, секция регламента «Варианты интерфейса — до
кода, не после». Включается, когда задача **добавляет или
переставляет видимый элемент** — колонку, кнопку, поле,
модальное окно, экран, блок страницы. Меняется только
поведение существующего (расчёт, блокировка поля, проверка) —
шаг пропускается молча, вопросов не задавать. Сомнение —
спросить пользователя (правило 8).

Показать **ровно три принципиально разных** варианта: разная
компоновка, разный способ взаимодействия, разное место в
интерфейсе. Три оттенка одной идеи — нарушение: выбирать не
из чего.

- **новый элемент** → мокап-страница в `static/mockups/`: один
  HTML-файл, три варианта друг под другом с заголовками
  «Вариант 1/2/3» и разбором плюсов-минусов; данные фиктивные,
  но правдоподобные; оформление из `static/css/variables.css`;
- **сдвиг существующего элемента, смена подписи** → скетч или
  описание прямо в чате, без файла;
- **ЗАПРЕЩЕНО** встраивать варианты в живой интерфейс под
  переключателем — это уже реализация.

Ход, ожидающий выбора, заканчивать явным призывом: «Жду вашего
выбора: вариант 1, 2 или 3». Кода не писать до ответа.

Мокап временный: `static/mockups/` в `.gitignore`, в репозиторий
файлы не попадают. Поэтому выбор дописать в заметку ТЕКСТОМ
(секция «Что именно делаем»): какой вариант и почему, коротко —
чем плохи отвергнутые. Ссылок на файл мокапа в «Связях» не
ставить: он не переживёт переноса.

### Шаг 4. Код

Перед написанием своей реализации — **проверить, есть ли
готовое** (см. vault «Готовое решение вместо своего»): назвать
1–3 подходящие библиотеки с лицензиями и предложить выбор
пользователю. Самописный код — только по согласованию, с записью
аргумента в заметку. Не относится к бизнес-логике проекта — она
своя по определению.

Фаза → `код`. По ходу — обновлять заметку, если решения меняются
относительно согласованного.

### Шаг 5. Тесты и показ интерфейса

`python -m pytest tests/ -x -q` — все зелёные. Фаза → `тесты`.
Хук на коммите прогонит тесты ещё раз и заблокирует красные,
но гонять надо ДО попытки коммита — не жечь время на
заблокированных коммитах.

**Менялся интерфейс — показать результат** (правило 14 устава):
открыть готовую страницу в браузере (панель Browser) и назвать,
что изменилось. Вход в приложение — учётная запись `admin` с
паролем `admin` в локальной базе разработки; нет её — создать
командой `python manage.py ensure_admin`. Данные годятся ТОЛЬКО
для дев-базы, в закрытый контур такой пароль не переносится.
Отписка «в браузере не проверял» недопустима: либо показ, либо
названная причина, почему он невозможен.

### Шаг 6. Коммит

Фаза → `коммит`. В сообщении — явная ссылка на заметку:
`feat(works): ... (vault: «Имя заметки»)`. Хук `check_commit.py`
без ссылки (или пометки «журнал мелких правок», или метки-
исключения: косметика / линтер / опечатка / откат) коммит
не пропустит.

### Шаг 7. Закрытие — чек-лист (Definition of Done)

Проверить СОДЕРЖАТЕЛЬНОЕ (руками):

1. Секция «Как проверим» пройдена фактически — каждый пункт
   проверен, а не «на глаз».
2. Изменившиеся по ходу решения отражены в заметке.
3. **Остатки задачи получили дом** (правило 16 устава, ADR
   «Закрытие задачи — остатки и видимые изменения»): каждый
   оставшийся пункт — в разделе «Осталось после задачи» со ссылкой
   `[[заметка]]`, строкой «долг №N» реестра или пометкой «не
   задача: причина». Остатков нет — прочерк «—». Нет раздела у
   задачи, закрытой с 06.10.2026, — валидатор vault завернёт
   закрывающий коммит.
4. **Вид интерфейса назван** — если «Затрагивает» упоминает
   `templates/`, `static/` или панель Django: раздел «Вид
   интерфейса» говорит либо «вид не меняется», либо выбранный
   вариант и адреса страниц.
5. Память обновлена: `current_task.md`, при необходимости —
   тематические файлы и строка в `MEMORY.md`.

БУХГАЛТЕРИЮ делает скрипт автозакрытия (запускает ассистент):

```bash
python .claude/hooks/close_task.py
```

- полная форма: хэш в «Историю», статус `сделано`, закрывающий
  коммит, табло очищено;
- малая форма: `--desc "что сделано" --files "какие файлы"` —
  строка в журнал + закрывающий коммит.

Скрипт сам гоняет валидатор vault и откажется закрывать грязное.

После закрытия КРУПНОЙ задачи — предложить пользователю
прогнать `/consolidate-memory` (уборка памяти).

## Что НЕ требует этой процедуры

Косметика, авто-фиксы линтеров, опечатки, откаты собственных
ошибок, автоген-файлы (`/graphify`) — по регламенту в vault не
попадают, навык не нужен. В коммите поставить метку-исключение
(«косметика», «линтер», «опечатка», «откат») — иначе хук
заблокирует.
