# Навык reglament-setup — мастер настройки системы управления разработкой

## Зачем эта система

Большой проект не помещается в контекстное окно ИИ-ассистента, а
между сессиями ассистент ничего не помнит. Решение — вынести
память в файлы. Система из четырёх слоёв:

| Слой | Файл / место | Роль |
|---|---|---|
| Устав | `CLAUDE.md` в корне проекта | Короткие жёсткие правила; ИИ видит автоматически каждую сессию |
| Документация | `docs/vault/` в репозитории | Оригинал знаний: регламент, описания модулей, заметка на каждую задачу с историей коммитов. Переносимо, читаемо человеком |
| Память ИИ | `~/.claude/projects/<проект>/memory/` | Кэш: конспекты ассистента, восстановимы из vault и кода |
| Статус | `current_task.md` в памяти ИИ | Что в работе, где остановились — преемственность сессий |

Рабочий цикл после настройки: задача → заметка в vault →
согласование с пользователем → код → тесты → коммит со ссылкой
на заметку → хэш коммита в заметку → обновление памяти.

## Железные правила мастера

1. **Ни один файл не создаётся и не меняется без явного
   подтверждения пользователя.** По одному файлу за раз:
   показать проект содержимого → дождаться «да» или правок →
   только потом записать → перейти к следующему.
2. **Ничего не выдумывать про проект.** Всё проектное (стек,
   команды, конвенции) — только из ответов пользователя; где
   ответа нет — оставить прочерк «—» с пометкой «заполнить
   позже».
3. Язык общения и всех создаваемых файлов — тот, который
   пользователь выбрал на шаге 1. Этот файл написан по-русски,
   но при выводе пользователю все тексты, вопросы, принципы и
   шаблоны переводить на выбранный язык.
4. При сомнении в любом шаге — остановиться и спросить.
5. **Каждый вопрос пользователю — с мини-комментарием** по
   схеме: *что это* → *зачем спрашиваю* → *куда пойдёт ответ*.
   Пользователь может не быть профессиональным разработчиком;
   вопрос без контекста заставляет гадать. Комментарий — 1–3
   предложения, не лекция.

## Шаг 0. Предохранитель (обязательно, до любых действий)

Проверить признаки уже настроенного проекта:

- существует `docs/vault/_meta/Регламент.md`, ИЛИ
- существует `CLAUDE.md`, в котором упоминается vault/регламент.

Если хотя бы один признак есть — вывести: «Проект уже настроен,
мастер не применяется. Для ведения задач используйте проектный
навык (обычно `/reglament`)» — и **остановиться полностью**.

Дополнительно: если папка не является git-репозиторием —
предложить `git init` (система рассчитана на git; без него
хэши коммитов в заметках не работают).

## Шаг 1. Обзор и согласие

Начать на языке, на котором пользователь обратился (или на
языке интерфейса его сообщений). Самым первым вопросом
уточнить язык: «На каком языке вести настройку и создавать
файлы проекта (диалог, устав, документация)?» — и дальше весь
мастер, включая генерируемые файлы и проектный навык задач
(шаг 7), вести строго на выбранном языке.

Затем ОБЯЗАТЕЛЬНО объяснить, для чего мастер сделан и чем
полезен. Формат (переводить на выбранный язык):

> **Мастер настройки системы управления разработкой.**
>
> **Для чего он сделан.** У ИИ-ассистента ограниченное
> контекстное окно, а между сессиями он не помнит ничего.
> Большой проект в таких условиях вести нельзя — если не
> вынести память в файлы. Мастер разворачивает в проекте
> такую файловую систему памяти: устав с правилами,
> документацию с журналом решений, конспекты ассистента и
> файл текущего статуса.
>
> **Чем это полезно вам:**
> - новая сессия ассистента за минуту восстанавливает полный
>   контекст проекта — вместо получаса пересказов;
> - каждая задача сначала согласуется словами (заметка), потом
>   пишется код — ошибки ловятся до реализации;
> - история решений с привязкой к коммитам не теряется — через
>   полгода видно, почему сделано именно так;
> - документация читаема человеком и лежит в git — проект можно
>   передать другому разработчику или на другую машину.
>
> Настройка идёт пошагово: каждый принцип и каждый файл я
> покажу и дождусь вашего подтверждения — без него ничего не
> создаётся.

После этого вывести: таблицу четырёх слоёв (из раздела «Зачем»
выше), рабочий цикл и список шагов мастера (2–8). Спросить:
«Начинаем настройку?» Без «да» дальше не идти.

## Шаг 2. Опрос о проекте

Задать вопросы (можно одним сообщением, это факты, а не
принципы), каждый — с пояснением по правилу 5. Формат:

> 1. **Название и суть проекта** — одним-двумя предложениями.
>    *Зачем:* пойдёт в заголовок устава (CLAUDE.md) и README
>    документации — любая новая сессия сразу поймёт, о чём проект.
> 2. **Стек** — языки, фреймворк, база данных.
>    *Зачем:* секция «Стек» устава; ассистент будет опираться
>    на неё при написании кода, не переспрашивая каждый раз.
> 3. **Команда запуска** — как поднять проект локально.
>    *Зачем:* попадёт в устав; ассистент использует её, чтобы
>    самому проверять, что проект работает после правок.
> 4. **Команда тестов.**
>    *Зачем:* устав + шаг «Тесты» будущей процедуры задач:
>    перед каждым коммитом ассистент прогоняет именно её.
> 5. **Язык общения** (он же — язык комментариев в коде).
>    *Зачем:* конвенция в уставе; на этом языке будут писаться
>    все заметки документации.
> 6. **Особые ограничения** — офлайн, закрытый контур, правила
>    деплоя, запрещённые технологии.
>    *Зачем:* станут жёсткими запретами в уставе — то, что
>    ассистент не должен нарушать никогда.

«Пока не знаю» — допустимый ответ: в файле будет прочерк с
пометкой «заполнить позже».

## Шаг 3. Устав — CLAUDE.md

Показ проекта файла предварить пояснением (правило 5): что это
за файл (единственный, который ассистент видит автоматически в
начале КАЖДОЙ сессии), зачем он (короткие жёсткие правила —
«памятка новому сотруднику в первый день»), почему он должен
оставаться коротким (загружается целиком каждую сессию — длина
стоит места в контексте).

Показать проект файла с секциями: регламент документации
(краткие правила + ссылка на полный), запуск проекта, запуск
тестов, стек, структура проекта, конвенции кода, правила
работы (коммиты, деплой, стиль общения). Заполнить из ответов
шага 2, остальное — прочерки. Подтверждение → записать.

## Шаг 4. Принципы регламента — ПО ОДНОМУ

Шаг предварить пояснением: сейчас будут согласованы правила,
по которым пойдёт ВСЯ дальнейшая работа над проектом; из
подтверждённых принципов соберётся файл-регламент, и ассистент
будет обязан им следовать в каждой задаче.

Каждый принцип показать отдельно, по схеме: формулировка →
*что это значит на практике* (что ассистент будет делать или
перестанет делать) → *зачем* (какую проблему закрывает) →
вопрос «оставляем / меняем / выкидываем?». Список принципов:

1. Документация ведётся в vault внутри репозитория (общая
   история с кодом, переносимость).
2. Перед задачей сначала читать vault, потом код (страховка от
   правок вслепую).
3. На любое требование — сначала проект заметки в чат,
   согласование, сохранение (спецификация до реализации).
4. Никакого кода без согласованной заметки (запретная форма
   правила 3).
5. В коммите — ссылка на заметку (связь код ↔ документация).
6. После выполнения — дописать в заметку хэш коммита (история
   фичи в самой заметке).
7. При сомнении — остановиться и спросить пользователя.
8. Автогенерируемые файлы — исключение из правил 3/5/6.
9. Память ИИ: файл статуса `current_task.md` обновляется в
   конце каждой сессии с незакрытой задачей; после крупных
   задач — уборка памяти (`/consolidate-memory`).
10. Всё, что ассистент обязан делать регулярно, выносится в
    скрипт-хук. Инструкция в тексте регламента — временная
    мера до появления скрипта. Если ассистент забыл шаг
    дважды — это повод написать скрипт, а не ужесточить
    формулировку.

Из подтверждённых принципов собрать `docs/vault/_meta/Регламент.md`
(каждый принцип — с абзацем-обоснованием), показать файл
целиком → подтверждение → записать.

## Шаг 5. Структура vault и шаблон заметки

Предварить пояснением: vault — это папка обычных
markdown-заметок в репозитории, главное хранилище знаний
проекта (удобно читать через Obsidian, но это не обязательно);
сюда будут писаться заметки о каждой задаче и решении, и именно
эта папка переедет вместе с проектом куда угодно. Шаблон нужен,
чтобы все заметки имели одинаковую структуру и ничего не
забывалось.

Предложить структуру (папки создаются по мере появления первых
заметок, пустые не плодить):

```
docs/vault/
├── README.md        ← вход для нового человека
├── _meta/           ← регламент, шаблоны
├── модули/          ← описания частей системы
├── задачи/          ← заметка на каждую задачу
└── архитектура/     ← принятые решения (ADR)
```

И шаблон заметки задачи (`_meta/Шаблон — задача.md`) со
скелетом секций: Зачем / Что именно делаем / Затрагивает /
Бизнес-правила / **Как проверим** / Связи / История.

Правила шаблона (объяснить пользователю, включить в Регламент):

- «Как проверим» обязательна: 2–5 проверяемых утверждений на
  языке пользователя; рекомендуемый формат «дано → когда →
  тогда». Без секции заметка не согласовывается.
- «Не угадывать»: недосказанное в требовании ассистент помечает
  маркером отдельной строкой «⚠️ уточнить: …»; заметка с
  неснятыми маркерами не согласовывается.
- Словари строгие (перевести на язык проекта): статусы задач —
  запланировано / в работе / сделано / заморожено; статусы
  постоянных документов — действует / заменено; типы — задача /
  баг / решение (ADR) / модуль / meta / автоген.
- **Малая форма**: правка в 1–2 файлах без изменения
  бизнес-правил, без новых зависимостей и миграций — вместо
  отдельной заметки строка в журнале
  `задачи/Мелкие правки (журнал).md` (таблица: дата / что
  сделано / файлы / хэш); согласование всё равно обязательно.

Подтверждение → создать README, Регламент (из шага 4), шаблон
и журнал мелких правок (пустая таблица с шапкой).

## Шаг 6. Память ИИ и файл статуса

Предварить пояснением: у ассистента есть личная папка памяти
для этого проекта (вне репозитория, на этой машине) — его
«конспект». В отличие от vault, её никто не переносит и не
читает, кроме ассистента: это кэш для скорости, при потере
восстановим из vault и кода. Зачем настраивать сейчас: чтобы
уже вторая сессия начиналась с «я всё помню», а не с чистого
листа.

Объяснить файлы: `MEMORY.md` — оглавление памяти (грузится
каждую сессию, одна строка на тему), `current_task.md` —
текущий статус: что в работе, где остановились (читать
первым; страховка от обрыва сессии посреди задачи). Создать
оба в папке памяти проекта; в `MEMORY.md` — первой строкой
ссылку на `current_task.md`. Подтверждение → записать.

## Шаг 7. Уровень принуждения и проектный навык ведения задач

Предварить пояснением: навык — это файл-инструкция, который
ассистент выполняет как чек-лист по команде `/reglament`:
правила регламента превращаются в пошаговую процедуру. У
процедуры два уровня исполнения — объяснить и спросить:

> Регламент можно вести на двух уровнях.
>
> - **Промптовый**: навык-инструкция. Работает, но держится на
>   дисциплине языковой модели — в длинных сессиях процедура
>   может «выветриться».
> - **Детерминированный** (рекомендуется): плюс табло задачи
>   (машиночитаемый файл состояния) и хуки — скрипты-перехватчики,
>   которые физически блокируют правку кода до одобрения заметки,
>   коммит без ссылки на документацию и красные тесты; одобрение
>   ставит только пользователь (штамп кнопкой Run), закрытие
>   задачи делает скрипт. «Забыть» невозможно.
>
> Ставим хуки принуждения? **да** (рекомендуется) / **нет**
> (только промптовый уровень) / **отложить** (запишу вопрос в
> файл статуса — решите, когда поработаете).

Затем создать в проекте `.claude/skills/reglament/SKILL.md` —
процедуру ведения задачи, заполненную ответами пользователя
(команда тестов — из шага 2, принципы — из шага 4), на языке
проекта. При «да» — детерминированный скелет (ниже); при «нет»
или «отложить» — упрощённый: те же шаги без табло, штампа,
наблюдателя и скриптов (согласование словами, закрытие заметки
вручную), а при «отложить» ещё дописать вопрос в
`current_task.md`. Скелет (детерминированный вариант):

```markdown
---
name: reglament
description: >
  Пошаговая процедура регламента для новой задачи по коду или
  архитектуре. Вызывать в начале КАЖДОЙ задачи: «/reglament»,
  «начинаем задачу», «по регламенту»; продолжение прерванной
  задачи — «/reglament продолжить».
---

# Навык reglament

Ведёт задачу по регламенту проекта
(docs/vault/_meta/Регламент.md — источник истины).

Слэш-команды (`/reglament` и другие) пользователь вводит в ПОЛЕ
ЧАТА. Никогда не оформлять их shell-блоком: у блока появится
кнопка Run, терминал такой команды не знает и вернёт ошибку.
Shell-блок — только для настоящих команд терминала (штамп,
закрытие задачи).

## Табло задачи — обновлять на каждом шаге

.claude/task-state.json (локальное, вне git) — машиночитаемое
состояние: задача, путь к заметке, фаза, форма, отметка
одобрения. Фазы: vault → заметка → согласовано → код → тесты →
коммит → закрыто. Хуки читают именно табло: gate_edit.py (блок
правок кода до одобрения), check_commit.py (блок коммита без
ссылки и запуска штампа ассистентом), check_turn_end.py (не даёт
замолчать без призыва к штампу и наблюдателя), validate_vault.py,
close_task.py.

## Вводная памятка (первым сообщением)

Короткая (по умолчанию): задача, форма (полная/малая), фаза,
предупреждение «код не правится до согласования заметки».
Полная (карта файлов системы: устав, vault, память, статус) —
только если память ИИ проекта пуста или по слову «памятка».

## Продолжение прерванной задачи

Незакрытая задача в табло (или «/reglament продолжить»):
прочитать табло → сверить с реальностью (заметка, git status,
current_task.md) → доложить «в работе „…", фаза „…", продолжаю
с шага N». Табло расходится с реальностью — спросить
пользователя, не угадывать.

## Шаги процедуры

0. Статус: табло + current_task.md + git status (чужие правки —
   выяснить у пользователя). Завести табло задачи: фаза vault.
1. Сначала vault, потом код.
2. Оценить размер. Малая форма (1–2 файла, без бизнес-правил,
   зависимостей и миграций): «это малая форма, делаю так-то» →
   подтверждение → фаза «согласовано»; после коммита закрыть
   close_task.py --desc ... --files ... Иначе показать ПРОЕКТ
   заметки по шаблону («Как проверим» обязательна; недосказанное
   — маркер «⚠️ уточнить», с маркерами не согласовывать). Фаза →
   «заметка». Не сохранять заметку, не править код.
3. Согласование (полная форма): после устного «согласовано»
   показать команду штампа отдельным bash-блоком (у пользователя
   будет кнопка Run; слэш-команды, наоборот, в bash-блоки не
   оформлять — см. правило выше):

       python .claude/hooks/approve_task.py

   Ассистенту запуск запрещён хуком — не пытаться. СРАЗУ после
   показа поставить фонового наблюдателя (инструмент Bash,
   run_in_background), чтобы работа продолжилась сама и
   пользователю не пришлось писать в чат после нажатия Run:

       for i in $(seq 1 290); do grep -q '"одобрено": true' \
```

## Шаг 8. Хуки принуждения (если на шаге 7 выбран «да»)

Рядом с этим файлом мастера лежит папка `templates/` — готовые
скрипты слоя принуждения. Создать в проекте:

| Файл в проекте | Шаблон | Что делает |
|---|---|---|
| `.claude/hooks/gate_edit.py` | `templates/gate_edit.py` | блокирует правку кода до согласования; пустое табло — напоминание, не блок |
| `.claude/hooks/check_commit.py` | `templates/check_commit.py` | блокирует коммит без ссылки на vault / пометки журнала / метки-исключения и запуск штампа ассистентом; гоняет валидатор на vault-коммитах |
| `.claude/hooks/validate_vault.py` | `templates/validate_vault.py` | словари статусов и типов, хэш у «сделано», секция «Как проверим», маркеры «уточнить», битые ссылки |
| `.claude/hooks/close_task.py` | `templates/close_task.py` | автозакрытие: хэш и статус в заметку (или строка в журнал), закрывающий коммит, очистка табло |
| `.claude/hooks/approve_task.py` | `templates/approve_task.py` | штамп одобрения — запускает ТОЛЬКО пользователь |
| `.claude/hooks/check_turn_end.py` | `templates/check_turn_end.py` | не даёт закончить ход, если заметка ждёт штампа, а призыв нажать Run не прозвучал или наблюдатель не запущен (принцип 10) |
| `.claude/hooks/pre-commit-tests.sh` | `templates/pre-commit-tests.sh` | тесты перед коммитом; красные — коммита нет |

При записи каждого файла:

- перевести сообщения, словари, метки и статусы на язык проекта
  — строго те же слова, что в Регламенте, шаблоне заметки и
  навыке (хуки сверяют строки буквально);
- подставить плейсхолдеры: `{{КОМАНДА_ТЕСТОВ}}` — из анкеты
  (шаг 2), путь журнала мелких правок — реальное имя файла
  из шага 5;
- команда запуска в `settings.json`: на Windows — `python -X utf8`,
  на macOS/Linux — `python3 -X utf8` (голой командой `python`
  многие системы не располагают);
- пометки `[МАСТЕР: …]` — инструкции мастеру, в записываемые
  файлы их НЕ переносить.

Исключение из железного правила 1: хуки согласуются пакетом —
показать таблицу выше (что и зачем), содержимое любого файла по
запросу; после «да» записать все семь.

Дополнительно (тоже показать перед записью):

- `.claude/settings.json` — регистрация хуков по образцу
  `templates/settings-hooks.json`; существующий файл аккуратно
  дополнить, не затирая чужие настройки; statusMessage перевести.
- `.gitignore` — строка `.claude/task-state.json` (табло —
  локальный файл, вне git).
- ВАЖНО: сами хуки и `settings.json` должны попасть В git (не
  добавлять их в `.gitignore`) — иначе при переносе проекта на
  другую машину слой принуждения молча исчезнет.
